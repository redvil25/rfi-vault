# CLAUDE.md — Project Operating Manual

> Read this first in every session. It is the contract between the team and any AI agent working in this repo.

## 1. What this project is

**Codename:** NexaMinds RFI Repository (working product name: **RFI Vault**)

**Context:** Novo Nordisk GBS Hackathon 2026, Problem Statement #18 — *"Repository for Validation RFI considerations & responses received for EU CTR submissions."*

**One-line pitch:** A searchable, auditable repository of EU CTR Request-For-Information (RFI) considerations and approved sponsor responses that (a) finds precedent instantly, (b) predicts which sections of a *draft* application will trigger an RFI before submission, and (c) drafts grounded responses with citations.

**Deadline:** final submission ~11 September 2026 (one month from the 11 August 2026 kickoff). Confirm exact date with the Novo Nordisk mentor in Week 1.

**Deliverables to Novo Nordisk:**
1. Functional prototype / proof-of-concept (deployed, live URL).
2. Presentation demonstrating the solution and its value proposition.
3. Concise project report, **max 2 pages**.

**Judging weights:** Innovation 25% · Technical Implementation 25% · Business Impact 20% · Feasibility 15% · Presentation Quality 15%. Every engineering decision must be traceable to one of these.

## 2. Non-negotiable rules

1. **Dummy data only.** No real Novo Nordisk data, no real patient data, no scraped confidential documents. All corpora are synthetic and generated by our own scripts (`scripts/seed/`). IP is not applicable per hackathon rules, but confidentiality is — a Confidentiality Agreement exists between the college and Novo Nordisk GBS.
2. **The AI never invents regulatory facts.** Every generated response must cite retrieved source records by ID. If retrieval confidence is below threshold, the system refuses to draft and escalates. This is the single most important product behaviour — a pharma regulatory audience will disqualify a tool that hallucinates.
3. **EU data residency.** Supabase project in an EU region (`eu-central-1`, Frankfurt). Whatever host is chosen in Phase 3 must also be pinned to an EU region. Say this out loud in the demo — the audience is a Danish pharma company.
4. **Append-only audit trail.** `audit_events` rows can be inserted, never updated or deleted. Enforced by a database trigger, not by application code.
5. **Everything demoed must be reproducible.** `npm run seed` rebuilds the entire corpus from a fixed seed. No hand-edited database rows.
6. **Measure, don't assert.** Any claim in the deck ("hybrid search is better") must have a number behind it from `npm run eval`.

## 3. Tech stack (decided — see `docs/DECISIONS.md` for rationale)

| Layer | Choice |
|---|---|
| Framework | Next.js **16.3.0**, App Router, TypeScript, React 19.2.8, Server Components |
| UI | Tailwind CSS v4 + shadcn/ui + Recharts |
| Source control / CI | **GitHub** + GitHub Actions |
| Hosting | **Undecided — see ADR-011.** Deferred to Phase 3. Any Node host works (Render, Netlify, Cloudflare, self-host). Nothing in the codebase may depend on a specific host. |
| Database | Supabase Postgres + `pgvector` (HNSW) + `tsvector` full-text, EU region |
| Auth | Supabase Auth (email/password + magic link), RBAC via Postgres RLS |
| File storage | Supabase Storage (private bucket, signed URLs) |
| LLM | Google Gemini via **AI SDK v7** (`ai` + `@ai-sdk/google`, direct provider — no gateway) — `gemini-2.5-flash` for extraction/drafting, `gemini-2.5-pro` for the verifier pass |
| Embeddings | `gemini-embedding-001` (768-dim output configured), with a local `transformers.js` fallback if quota is exhausted |
| Validation | Zod v4 on every API boundary |
| Tests | Vitest (unit) + Playwright (E2E) |
| CI | GitHub Actions — typecheck, lint, unit, build; E2E enabled in Phase 3 |

**Host-portability rule.** Because the host is undecided, keep the app a plain Next.js application: no host-specific config files, no proprietary runtime APIs, no platform-only primitives. Long-running work goes in route handlers or scripts, not in a vendor queue product.

`AGENTS.md` is generated and re-written by `next dev`. Do not hand-edit it; commit it when it changes.

## 5. Commands

```bash
npm run dev              # local dev server
npm run build            # production build (must pass before every demo)
npm run typecheck        # tsc --noEmit
npm run lint
npm run test             # vitest
npm run test:e2e         # playwright
npm run db:migrate       # apply supabase migrations
npm run db:types         # regenerate lib/db/types.ts from the linked project
npm run seed             # regenerate synthetic corpus (deterministic, seed=42)
npm run seed -- --keep   # add to the existing corpus instead of wiping it
npm run verify           # live smoke test: RLS isolation, search, audit immutability
npm run ingest -- <pdf>  # parse a CTIS RFI export and print the extraction (read-only)
npm run fixtures:pdf     # regenerate fixtures/rfi-example-ctis.pdf (needs python + reportlab)
npm run eval             # retrieval + risk + groundedness metrics -> docs/metrics/latest.json
```

**Run `npm run verify` before every demo and after every migration.** It signs in as
real users and asserts the things unit tests cannot reach.

## 6. Conventions

- **TypeScript strict.** No `any` in `lib/`. Zod-infer types at boundaries.
- **Server Components by default.** `"use client"` only for interactive leaves.
- **Every AI call is typed.** Use AI SDK `generateObject` with a Zod schema — never parse free-text JSON.
- **Every AI call is logged** to `ai_calls` with model, prompt hash, token counts, latency, and cost. The analytics slide comes from this table.
- **Naming:** database `snake_case`, TypeScript `camelCase`, React components `PascalCase`, files `kebab-case`.
- **Migrations are forward-only** and numbered `0001_`, `0002_`. Never edit an applied migration.
- **Domain vocabulary is fixed.** Use the exact CTIS terms: *consideration*, *request for information*, *sponsor response*, *application section part*, *substantial modification*, *Member State Concerned (MSC)*, *Reporting Member State (RMS)*. See `docs/01-DOMAIN.md`. Getting the vocabulary right is a scoring signal with this audience.

## 7. Definition of done (per feature)

A feature is done when all of these are true:
- [ ] Happy path works against seeded data on the deployed preview URL
- [ ] Empty state, loading state, and error state all render
- [ ] Zod validation on the API route; invalid input returns 400 with a useful message
- [ ] RLS policy tested — a user from one team cannot read another team's draft
- [ ] Audit event emitted for every state-changing action
- [ ] At least one Vitest unit test on the core logic
- [ ] Covered by the demo script in `docs/06-DEMO-AND-DECK.md`
- [ ] A number in `docs/metrics/latest.json` if the feature makes a quality claim

## 8. Agent guardrails

When an AI agent works in this repo:
- Do not add dependencies without noting them in `docs/DECISIONS.md`.
- Do not change the database schema without a numbered migration.
- Do not weaken RLS policies to make a test pass.
- Do not put secrets in code — use `.env.local` locally and repository secrets in GitHub Actions.
- Do not fabricate regulatory timelines or article numbers. Everything in `docs/01-DOMAIN.md` marked **[VERIFY]** must be confirmed against EMA/EU CTR sources or the mentor before it goes in the deck.
- Prefer editing existing files over creating parallel ones. This repo is small on purpose.
